# 高效推进分工方案

本方案不追求三个人工作量完全相同，而是优先保证实验可以最快进入“能运行、能验证、能写报告”的状态。核心原则是：代码实现先行，测试验证同步准备，报告材料边做边收集。

## 总体目标

最终小组需要交付一套完整实验成果：

1. 可编译、可运行的 Go-Back-N 数据链路层协议代码。
2. 能证明协议正确性的测试记录、日志和性能数据。
3. 包含实验目的、实验原理、实现逻辑、关键代码、测试结果和分工说明的实验报告。
4. 可供老师检查的项目仓库，包括 README、源码、文档、测试记录和报告材料。

## 成员一：协议主实现

### 主要任务

成员一直接负责实验最关键的代码产物，以 `Lab1-linux/datalink.c` 为主开发文件，把现有停止等待式逻辑扩展为 Go-Back-N 滑动窗口协议。

需要完成：

- 设计发送窗口变量，例如 `ack_expected`、`next_frame_to_send`、`nbuffered`。
- 建立发送缓存，保存窗口内尚未确认的数据包。
- 修改 DATA 帧发送逻辑，使窗口未满时可以连续发送多个帧。
- 实现累计 ACK 处理，收到确认后滑动发送窗口。
- 实现超时后的 Go-Back-N 重传，从最早未确认帧开始重发。
- 控制 `enable_network_layer()` 和 `disable_network_layer()`，窗口满时暂停从网络层取包。

### 最终交付

- 修改后的 `Lab1-linux/datalink.c`。
- 简短代码说明，写清楚主要变量含义、窗口滑动条件和重传逻辑。
- 至少一组能正常运行的基础测试结果，证明代码没有明显崩溃或死锁。

### 产出产品

成员一交付的是本实验的核心产品：Go-Back-N 协议实现。

## 成员二：调试验证与性能测试

### 主要任务

成员二不等成员一完全写完才开始工作，而是先准备测试方案和记录模板。成员一代码可运行后，成员二马上接手验证，找出协议问题并反馈。

需要完成：

- 设计测试场景和命令，包括无误码、默认误码、满负载和高误码场景。
- 运行 A、B 两端程序，保存关键日志和性能输出。
- 检查是否存在重复交付、乱序交付、ACK 错误、超时后不重传、窗口不滑动等问题。
- 统计吞吐率、误码率、重传现象和稳定性表现。
- 将发现的问题及时反馈给成员一，帮助定位代码缺陷。

推荐测试场景：

```bash
# 无误码环境，验证基本正确性
./datalink -u A
./datalink -u B

# 默认信道，验证 CRC 和超时重传
./datalink A
./datalink B

# flood 模式，验证窗口协议吞吐能力
./datalink -f A
./datalink -f B

# 高误码环境，验证协议稳定性
./datalink -f -b 1e-4 A
./datalink -f -b 1e-4 B
```

### 最终交付

- `tests/` 目录下的测试命令记录。
- `reports/` 目录下的性能测试表或截图材料。
- 关键日志摘要，说明每个测试场景是否通过。
- 问题清单，记录测试中发现的问题和最终解决情况。

### 产出产品

成员二交付的是实验可信度产品：测试证据和性能分析材料。

## 成员三：报告整合与答辩材料

### 主要任务

成员三负责把实验过程整理成最终可提交材料。成员三应从一开始就跟进代码和测试进展，不等最后才补报告。

需要完成：

- 阅读实验指导书，整理实验目的、实验环境和实验要求。
- 根据成员一的代码说明，整理 Go-Back-N 实现原理。
- 根据成员二的测试结果，整理性能测试和结果分析。
- 绘制或整理协议流程，包括发送端流程、接收端流程、ACK 处理和超时重传流程。
- 完成最终实验报告初稿，并统一格式、截图、表格和小组分工说明。

报告建议结构：

1. 实验名称和小组成员。
2. 实验目的。
3. 实验环境与课程框架说明。
4. Go-Back-N 协议原理。
5. 程序设计与关键数据结构。
6. 关键代码说明。
7. 测试方案和测试结果。
8. 性能分析与问题总结。
9. 小组分工与个人贡献。

### 最终交付

- 最终实验报告文档。
- 报告中使用的流程图、截图和表格。
- README 中分工说明的最终版本。
- 答辩或检查时可直接说明的实验逻辑梳理。

### 产出产品

成员三交付的是最终提交产品：实验报告和展示材料。

## 并行推进方式

为了最快完成实验，三个人不要串行等待：

- 第一天：成员一开始改协议代码；成员二写测试命令和记录模板；成员三整理实验目的和协议原理。
- 代码能编译后：成员二立即跑无误码测试和默认信道测试；成员三同步记录关键实现逻辑。
- 代码基本稳定后：成员二跑 flood 和高误码测试；成员三把测试结果放入报告。
- 最后汇合：成员一补关键代码说明，成员二补测试结论，成员三统一报告和 README。

## 最终仓库应包含的产品

```text
.
├── Lab1-linux/datalink.c          # 最终协议实现
├── README.md                      # 项目说明、实验逻辑、总体分工
├── docs/efficient-division.md     # 高效推进分工方案
├── docs/experiment-plan.md        # 实验设计和协作计划
├── tests/                         # 测试命令、测试记录
├── reports/                       # 实验报告、性能表、截图和日志摘要
└── logs/                          # 需要保留的关键运行日志
```

最终检查时，只要能说明“代码如何实现可靠传输、测试如何证明正确、报告如何总结实验”，这次实验的交付链条就是完整的。
